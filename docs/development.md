# Project workflows

The repository's safety, performance, and review rules are in
[engineering.md](engineering.md).

## Start a project

From a new Git repository:

```sh
nix flake init -t /projects/USER/workstation#minimal
git add flake.nix .envrc .gitignore
nix flake lock
git add flake.lock
direnv allow
```

Replace `minimal` with `rust`, `python`, or `web`. All four templates support
x86_64 and aarch64 Linux. Rust requires a Cargo project and tracked Cargo.lock
before package/check builds; its checks include formatting, Clippy and tests.
Python uses `uv init` and `uv sync`; commit uv.lock. Web projects should commit
their pnpm lockfile.
Launch `nvim` inside the activated environment to discover its language servers.

The global environment contains navigation, editing and system-management tools.
Repository linters and Nix inspection utilities are provided by `nix develop`.
SDK versions and
language servers belong in each project's devShell. Each project gets its own
flake.lock plus the ecosystem's lockfile. Templates are starting points, not
complete applications. Generate their lockfiles inside the new project and commit
them alongside source files; Git flakes exclude untracked files.

Python/uv and Node/pnpm templates pin tools but do not turn all dependencies into
Nix derivations. For distributable Python builds add uv2nix/pyproject.nix; for
JavaScript use an appropriate Nixpkgs builder. The Rust template includes Crane
package, formatting, Clippy and test outputs once Cargo.toml, Cargo.lock and
sources exist. All four templates expose development shells for x86_64-linux and
aarch64-linux; the workstation host itself remains x86_64-linux.

The Rust shell puts Cargo build outputs in a directory keyed by the canonical
project path under `${XDG_CACHE_HOME:-$HOME/.cache}/cargo-targets`. On this
workstation that cache lives under `/local`, outside hourly project snapshots
and backups. Sources and lockfiles stay in Projects. Existing projects need the
same `CARGO_TARGET_DIR` policy explicitly; changing a template does not migrate
their old `target` directories. Build outputs can be regenerated after recovery.

For multi-service projects, add devenv within that project's repository and commit
devenv.lock. Keep services on loopback, and consciously choose whether their data
is disposable or stored under backed-up Projects. Do not start project databases
as global workstation services.

Rootless Podman is opt-in: after installation, merge `"containers": true` into
`installation.json`, then rebuild and boot. Before installation, you can instead
set `containers = true;` in `settings.nix`; saved JSON choices override that file.
It uses fixed
subordinate IDs. Its image/volume storage survives reboot under `/local`, which
has no backups. Disabling the option unmounts that storage without deleting its
backing files. Bind important database data
to an explicit project directory and export a database-consistent dump. Rootless
Podman is not a guarantee of compatibility with every Docker/Compose application.

Neovim supplies nixd and nixfmt in its own PATH; `nix develop` exposes them as
shell commands for repository maintenance. Other Neovim LSPs start only if present in
the launching project's PATH. Restart the editor after changing project shells.
Runtime editor plugins are declarative; there is no separate plugin downloader.
See [the tool policy](philosophy.md) for default responsibilities and optional
rich file previews.

## Repository layout

| Source | Responsibility |
| --- | --- |
| `lib/default-settings.nix` | Reusable workstation defaults |
| `settings.nix` | Defaults combined with installation-specific choices |
| `installation.json` | Local, ignored choices generated by the installer; overrides defaults |
| `hosts/workstation` | Generic hardware and declarative disk layout |
| `modules/nixos` | Boot, persistence, users, secrets, services, backups |
| `modules/home` | Niri, shell, editor and desktop applications |
| `scripts` | Installation, hardware policy, source snapshots and storage helpers |
| `checks` | Lint, configuration, unit and disposable VM checks |
| `hardware/graphics` | Prepared, integrity-checked compatibility data for the pinned release |
| `templates` | Project-local development environments |

The installation flake output is `workstation`, independently of your chosen
network hostname. NixOS and Home Manager use the same pinned package set.

## Shared defaults and local installations

`lib/default-settings.nix` defines the reusable defaults. `settings.nix` combines
those with `installation.json`, which the installer writes for the target machine.
The JSON file stays local and is ignored by Git. A fresh clone starts with the
shared defaults; the guided installer saves the machine's choices. `just build`,
`just diff`, `just switch`, and `just boot` include the local file through a
filtered source snapshot. Before a disk is selected, flake checks evaluate an
inert fixture and the host recipes refuse to build. The fixture host built in CI
has fixed test settings.
The shared timezone defaults to UTC; the installer asks for the target timezone.
Keep hardware-specific experiments and personal choices in installation overrides.
The graphics-profile and boot checks use a separate fixture identity and shared
defaults, so local hardware choices, credentials and backup settings do not leak
into the test machines. The complete host build still validates the selected
installation's configuration.

## Working on this repository

Enter `nix develop` for pinned tools and automatic Git hook installation. `.editorconfig`
sets shared whitespace defaults. `just fmt` formats Nix, shell and workstation
Python code; `ruff check scripts checks --fix` applies safe Python lint fixes.
Ruff's rules and Python 3.13 target live in `ruff.toml`.
`just graphics-update` enters that shell itself, so routine updates do not require
a globally installed Python interpreter or prior manual shell activation.

Use `just check-python` while changing installer or graphics logic. It runs Ruff
and the installer, graphics policy and metadata regression suites without building
graphics profiles or booting VMs. `just check-fast` also checks Nix, shell, workflow
syntax, relative Markdown links/anchors and Niri. `just check` runs the full
suite, and `just build` builds the host without activating it. Build/check recipes
refuse implicit lockfile updates.

The full-check runner builds the fast gate, discovers all check names, then
builds individual outputs with separate Nix evaluators. `lib.checkGroups` defines
the same members used by the aggregate suites; the runner covers those members
without evaluating their aliases again. Graphics profiles and their integration
checks run independently, preserving all five complete system builds. This
avoids retaining the whole suite or graphics matrix in one evaluation.
All outputs use one source snapshot,
completed builds stay cached, and the first failure stops the run with its exit
status. It runs the check derivations; use `nix flake check --no-build` separately
when auditing the flake output schema, on a machine with enough evaluation memory.

The `just` build and check recipes and installer use the same filtered snapshot:
tracked files, recognized non-ignored new source files, and local
`installation.json`. New source files work without staging them. Other ignored
files, arbitrary untracked files and `.git` stay out of the snapshot. Keep
private local files ignored. Run the local checks with:

```sh
just check-fast
just check
```

Direct Git flake commands such as `nix build .#checks.x86_64-linux.fast` still
exclude untracked source files and the ignored installation settings.

On the workstation, use the `just` recipes for routine validation. They run
foreground evaluation in a bounded user scope, while the configured Nix build
slice limits daemon workers. See [reliability](reliability.md) for the limits,
their failure behavior, and post-activation checks. A direct `nix` command does
not get the foreground limit.

The CI workflow runs fast checks before the full suite and fixture host build
on the same runner, retaining successful check outputs and downloaded packages. Actions
are pinned to commits, credentials are not retained in the checkout, and superseded
runs are cancelled. Dependabot proposes weekly action updates. Full validation
requires a builder with KVM; CI verifies that requirement explicitly. Large builds
can use a trusted remote builder or an explicitly configured binary cache.

## Updating dependencies

Run `just update` to update workstation flake inputs and regenerate the graphics
metadata tied to those pins. Review the lockfile, catalogue and manifest together,
then run `just check` and `just build`. A generator edit, even formatting, changes
its provenance hash and also requires `just graphics-update`. Do not hand-edit the
generator hash to bypass reproducibility checks. Keep NixOS and Home Manager
`stateVersion` unchanged during package updates. Each project created from a
template maintains its own lockfiles independently.

## Shared desktop palette

`lib/palette.json` owns the semantic color roles used by Foot, Yazi, Fuzzel,
Mako, Waybar, Neovim and the generated Niri configuration. `niri.kdl` is a
template; validate its generated output through `just check-fast`.
After editing the palette, run `just palette-update` to refresh the offline
preview's `docs/palette.js`. The fast gate rejects stale generated preview data.
The original comparison panel keeps historical state overrides; shared surfaces,
revised states and role values use the palette. Audit contrast again when changing roles.
